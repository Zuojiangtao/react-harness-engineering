# ADR 0004：依赖管理器切换到 pnpm

- 状态：已采纳
- 日期：2026-11-03

## 背景

项目最初用 npm 起底座：本机 pnpm 的默认 isolated 布局在文件沙箱里解析不了目录 junction，`package-lock.json` 因此被提交。现在本机已装 pnpm 12，且 `docs/plan/` 里的命令本来就是按 pnpm 写的——两套依赖管理并存，文档与 CI 开始分裂。

## 决策

1. 包管理器固定为 **pnpm 12.16.1**：`package.json` 的 `packageManager` 写死版本，只提交 `pnpm-lock.yaml`，删除 `package-lock.json`。
2. `pnpm-workspace.yaml` 设 **`nodeLinker: hoisted`**。
3. 迁移用 `pnpm import` 从 npm lock 导入精确版本，再 `pnpm install`，避免"切管理器顺带升级依赖"。
4. CI 用 `pnpm/action-setup@v4` + `pnpm install --frozen-lockfile`，缓存键切到 pnpm。

## 为什么是 hoisted

- pnpm 默认的 **isolated** 布局会在 `node_modules` 里建 junction；本机文件沙箱无法 `realpath` 目录 junction，Node 解析嵌套依赖时报 `Cannot find module 'is-number'`。pnpm 11 与 12 都能复现。
- **hoisted** 用真实目录替代 junction，`pnpm run verify` 才能在沙箱内跑通；代价是失去 pnpm 的严格 `node_modules`（幽灵依赖不再被自动拦下），由 ESLint `boundaries` 和本项目的依赖方向规则兜底。
- 继续用 npm 虽然能跑，但会让 `docs/plan/`、`.claude/commands/` 与 README 继续各说各话。

## 后果

- 正面：一套锁文件与一套命令；CI 安装更快；文档和 AI 代理的默认动作一致。
- 负面：hoisted 不是 pnpm 默认值，跨机器仍可能出现幽灵依赖；新依赖若带构建脚本，需要在 `allowBuilds` 里显式放行。
- 约束：不要提交 `package-lock.json`；`nodeLinker` 只写在 `pnpm-workspace.yaml`（pnpm 12 不读 `.npmrc` 里的 `node-linker`）；改回 isolated 前先在沙箱里跑一次 `pnpm run verify`。
